# 单机并发与消融说明

主表统一使用单机 8×A800、1M 上下文配置、78–90-token coding 输入、effort100 和固定 1,024-token 输出。C1–C256 全部重新测量，采用相同预热与计时窗口；复现命令见 [测试方法](../benchmarks/README.md)。

C 是客户端未完成请求数。增加 C 可以提高批处理效率，但服务端容量达到上限后会产生排队，吞吐不一定继续提高。原始记录保留 running/waiting、TTFT、端到端延迟与 KV 抢占，不能把 CUDA Graph 的验证 token 行数当作运行请求数。

消融在同机 C128 上逐步加入两项优化，其余设置保持一致：

| 阶段 | Dense 分派 | EP8 通信 |
|---|---|---|
| 基础配置 | Marlin | NCCL AG/RS |
| 加入 dense BF16 | 至少 32 行走 BF16 GEMM | NCCL AG/RS |
| 加入 custom EP8 | 至少 32 行走 BF16 GEMM | 满足条件时走 custom AG/RS |

两项开关为 `VLLM_AMPERE_DENSE_BF16_MIN_TOKENS` 与 `VLLM_SM80_EP8_CUSTOM_AG_RS`，三档分别设置为 `0/0`、`32/0`、`32/1`。修改环境变量后重启服务再测量。

基础配置已经包含 DSpark5、CUDA Graph、FP8 KV、EPLB 和其他适配补丁。因此这项实验测量两项增量优化，不是从原始框架开始累计加速。每档两次结果全部保留，吞吐可能受到生成内容和专家分布影响；两次均值不代表统计显著性。

短请求固定输出使用 `ignore_eos=True`，适用于容量比较。完整 agent 评测使用自然生成、实际工具执行与 verifier，单独报告任务分数。历史长工具记录回放的输入为 20,593–73,688 token，使用自然 EOS 和前缀复用，不能与短请求数字混为同一负载。

历史 512K 配置的单机长请求持续吞吐：[C128 为 1,835.34 tok/s](../benchmarks/results/round13/remote-c128-repeat1/measurement-summary.json)，[C256 为 1,905.89 tok/s](../benchmarks/results/round14/remote-long-c256/measurement-summary.json)。两组均预热 360 秒、测量完整 600 秒；这是之前的长请求结果，不是本次 1M 短请求扫描。
