# 前缀缓存失效溯源

本次问题出现在持续增长的 Agent 工具负载中。固定历史回放仍能达到约 1,918–1,973 output tokens/s；该数字不能代表本次负载。

## 观测结果

评测开始后，前缀命中率随历史长度增长而下降：

| 时间段 | 输入中位数 | token 命中率 | 首 token 等待中位数 |
|---:|---:|---:|---:|
| 0–45 分钟 | 22.7K–93.5K | 93.3–96.4% | 0.9–1.2 s |
| 60–120 分钟 | 103.9K–124.2K | 72.3→33.7% | 8.6→45.1 s |
| 135–345 分钟 | 122.7K–143.9K | 22.1%→约 0% | 110.5→481.2 s |

最近 200 对同一会话的相邻请求全部在同一个 DP，工具间隔中位数 1.39 秒，但缓存命中仍为 0。原生 `/tokenize` 核验的一对请求前后分别为 109,431 和 111,162 token，最长公共前缀完整覆盖前一个输入；因此不是消息拼接变化、分词器漂移或跨 DP 路由造成的失配。

## 代码路径与原因

DeepSeek-V4.1 是混合 KV 模型。当前服务启动时记录的组块大小为 `[32, 32, 32, 32, 128, 8]`，LCM 调度粒度为 128；压缩 MLA、indexer、SWA 和 compressor 状态共用一个 `BlockPool`。一次命中只有在协调器能够为各个必需组找到同一前缀边界时才可复用，任一关键组被淘汰都会把可复用前缀截短到更早的边界。

服务为每个 DP 预留约 5,395,756 个 token 的 KV 预算。这是活跃请求的规划容量，不是保证所有已经完成会话都能保留的硬上限。评测进入约 25 个并发长会话后，活跃历史本身已接近数百万 token；新会话不断提交并释放尾部块，LRU 队列会淘汰旧前缀。DSpark 的末尾重算块还会让相同 hash 出现多个物理映射，进一步减少有效保留量。混合组的最短命中决定最终结果，于是命中率会从高位逐步跌到零。

服务端 30 秒计数器同时显示：命中增量为 0、local compute 约 12.4K token/s、decode 约 162 token/s；请求 queue 平均约 428 秒，prefill 平均约 17.5 秒，decode 平均约 1,055 秒。这解释了为什么 GPU 利用率仍为 100%：设备在重复做长 prefill 和低并发 decode，并不表示缓存路径健康。

## 已排除和未排除的因素

- 已排除：额外占卡进程、DP 迁移、请求间长空闲、客户端分词长度错误、thinking 字段单独漂移。
- 未证明：某一个 KV 组先被淘汰的精确顺序，以及重复物理块和 SWA 可达边界各自的比例。现有日志没有逐组命中计数。
- 当前没有运行时补丁注入正式评测。这样可以保持分数和吞吐结果可审计。

## 后续修复顺序

1. 在隔离服务上增加逐 KV 组命中／淘汰计数，确认最先失效的组。
2. 实测已有的重复块去重与部分前缀别名保护补丁；CPU 元数据测试已通过，但尚无 GPU 吞吐证明。
3. 比较原生 CPU KV offload 与更公平的 prefill/decode admission，避免长 prefill 把可复用 decode 前缀挤出池外。
4. 在相同增长历史、相同并发下重新测完整窗口；只有缓存命中率和持续 tokens/s 同时改善，才提升默认配置。
